  问题 3 / 与现有 ToolRegistry 的关系（这是最关键的架构岔路）

  AgentOrchestrator 现在的调用是：

  .toolNames(toolRegistry.getNames())

  ToolRegistry 的发现逻辑硬编码在 Function 接口 + @Description + 包路径
  com.dawn.ai.agent.tools。但：

  - MCP 暴露的是 ToolCallback（带 input schema），不是 Function
  bean，也不在那个包下。
  - Skill 既不是 Function 也不是 Tool——它是一段"按需展开的指令文本"，但需要在
  system prompt 里告诉模型"有什么 skill 可用"以及怎么取。

  两种集成模式：

  Column 1: ToolRegistry 改造
  Pattern A：统一抽象: 抽出 ToolDescriptor（name/description/callback），本地
    Function 与 MCP 都映射进来
  Pattern B：双轨制: 不动，新增 McpToolProvider、SkillRegistry 并列
  ────────────────────────────────────────
  Column 1: AgentOrchestrator 改动
  Pattern A：统一抽象: 几乎不动，仍调 toolRegistry.getNames()
  Pattern B：双轨制: 需改成
    .toolNames(...).toolCallbacks(mcpProvider.getCallbacks())
  ────────────────────────────────────────
  Column 1: TaskPlanner 看到的工具
  Pattern A：统一抽象: 一次性拿到全部（本地+MCP），规划准确
  Pattern B：双轨制: 默认只看本地；要让规划用上 MCP 得手动合并
  ────────────────────────────────────────
  Column 1: ToolExecutionAspect 拦截
  Pattern A：统一抽象: 自动覆盖（统一抽象）
  Pattern B：双轨制: MCP 走 Spring AI 自己的链路，AOP 不会拦到——指标/trace
    会缺一截
  ────────────────────────────────────────
  Column 1: 命名冲突处理
  Pattern A：统一抽象: 在 Registry 里集中决策
  Pattern B：双轨制: 散在两处

  我强烈推荐 Pattern A。三点理由：

  1. ToolExecutionAspect 是项目现在的 trace/metrics 中枢（StepCollector
  收集步骤、ai.rag.dedup.skipped 之类的计数器都靠它）。如果 MCP 工具绕开
  Aspect，SSE stream 里 step 事件就会少调用，前端时间线会出现 MCP
  调用的"鬼步骤"——这是 Iron Law Article 2「No AI slop pattern」的踩坑前兆。
  2. TaskPlanner 现在拿 toolRegistry.getDescriptions() 喂给规划 LLM；若 MCP
  工具不进来，"plan 出来的步骤"和"实际可用的工具集"就不一致，会反复触发
  fallback。
  3. Skill 虽然不是 tool，但完全可以用同一抽象：每个 skill
  注册为一个特殊的"虚拟工具" skill:{name}，模型调用它就等价于"展开这个 skill
  的完整内容并注入到下一轮上下文"——这正是 Anthropic 原版 progressive disclosure
  的 Java 落地方式。三件事（本地 Function / MCP Tool / Skill）共用一个出口。

  Pattern A 的代价是：ToolRegistry 要重构（不再强绑
  Function），但本身就是这次工作的应有之义。

  老大同意走 Pattern A 吗？还是希望保守一些（B）？

  问题 4 / MCP 传输协议：STDIO 还是 SSE

  Spring AI 1.1 的 MCP Client 是两个 starter：

  - spring-ai-starter-mcp-client —— STDIO，把 MCP server 作为子进程拉起，通过
  stdin/stdout 通信。
  - spring-ai-starter-mcp-client-webflux —— SSE / Streamable HTTP，纯 HTTP
  调用，需要远端有运行中的 MCP server。

  两者可共存，但每多一个 starter 都有代价（依赖、配置、心智）。

  ┌────────┬─────────────────────────────────────────────────┬─────────────┐
  │        │                      STDIO                      │  SSE/HTTP   │
  ├────────┼─────────────────────────────────────────────────┼─────────────┤
  │        │ 主流。@modelcontextprotocol/server-filesystem、 │ 少数。多用  │
  │ 生态适 │ -github、-postgres、-slack 等几十个开源 server  │ 于 SaaS 化  │
  │ 配     │ 默认就是 STDIO                                  │ MCP         │
  │        │                                                 │ 或自建服务  │
  ├────────┼─────────────────────────────────────────────────┼─────────────┤
  │ 启动依 │ 容器内需装好 MCP server                         │ 远端 URL    │
  │ 赖     │ 命令（npx、uvx、二进制等）——要改 Dockerfile     │ 即可，零本  │
  │        │                                                 │ 地依赖      │
  ├────────┼─────────────────────────────────────────────────┼─────────────┤
  │ 鉴权   │ 不需要（子进程信任边界）                        │ 要做 Bearer │
  │        │                                                 │ /OAuth      │
  ├────────┼─────────────────────────────────────────────────┼─────────────┤
  │ 故障模 │ 子进程崩溃需 supervisor 重启；stdout/stderr     │ 网络抖动、  │
  │ 式     │ 隔离要小心                                      │ 超时重试    │
  ├────────┼─────────────────────────────────────────────────┼─────────────┤
  │        │ dawn-ai 是 Spring MVC，加 WebFlux starter       │             │
  │ 项目契 │ 会引入 reactor 第二条链路，和现有               │ 同样要加    │
  │ 合度   │ Hooks.enableAutomaticContextPropagation()       │ WebFlux     │
  │        │ 共存可以但要测                                  │             │
  └────────┴─────────────────────────────────────────────────┴─────────────┘

  我推荐 STDIO-only 起步，理由：

  1. 学习/演示项目的最大价值是"能跑通主流生态"——接 mcp-server-filesystem 让
  agent 能读本地文件，比接一个空架子的远程 SSE server 演示效果好得多。
  2. 零额外鉴权设计，能聚焦在"接入"本身，不被 OAuth 这层杂事拖住。
  3. 未来加 SSE 是单纯加 starter 的事（Spring AI 的抽象层一致），不会推倒重来。
  4. 现有 docker-compose.yml 已经有完整的服务网格，再叠 SSE
  端点会让本地启动变重。

  代价：Dockerfile 要装 node（最常见的 MCP server
  runtime），镜像会胖一些。Dockerfile.dev 已经在的话改动很小。

  反对意见：如果老大压根不打算在 Docker 里跑 MCP（开发期 host 直跑），那
  Dockerfile 改动这条就不存在。

  老大选 STDIO-only，还是希望一上来就 STDIO + SSE 都支持？

  问题 5 / MCP server 列表的配置形态 + secret 管理

  SSE 模式下每个 MCP server 至少需要：name、url、auth（Bearer token /
  OAuth）、timeout。这一坨配置往哪儿放、secret 怎么注入？

  三种选项：

  (A) application.yml + 环境变量占位（Spring AI 官方默认 schema）
  spring.ai.mcp.client.sse.connections:
    github:
      url: https://mcp.github.com/v1
    internal-jira:
      url: https://mcp.internal.com/jira

  # headers 在 yml 里用 ${...} 引环境变量
  spring.ai.mcp.client.request-timeout: 30s
  secret 通过 env 注入，和现有 OPENAI_API_KEY 是同一个模式（README 第 30 行）。

  (B) 独立 mcp-servers.json（Claude Desktop / Cursor 风格）
  { "mcpServers": { "github": { "url": "...", "headers": { "Authorization":
  "Bearer ${GH_TOKEN}" } } } }
  独立文件，未来想接入 Claude Desktop 生态时可以直接复用。

  (C) DB 表 + Admin API
  运行时动态增删，无需重启。

  我推荐 (A)，理由：

  1. 和项目现有配置风格统一——application.yml 已经管着
  LLM、embedding、RAG、Redis、Postgres，再加 MCP 是自然延伸；独立 JSON
  文件会让"我去哪儿改配置"这件事变碎。
  2. Spring AI 1.1 的 MCP starter 原生认这套 schema——直接生效，无需自写
  ConfigurationProperties 解析器。
  3. secret 走环境变量和现有 BASE_URL/OPENAI_API_KEY 一致，docker-compose
  那一层不用做特殊处理。
  4. (B) 的"复用 Claude Desktop JSON"价值在 dawn-ai
  这种服务端场景几乎用不到——这是桌面客户端的格式。
  5. (C) 是真正生产化的形态，但当前阶段引入 Admin API + 鉴权 + 审计
  是过度设计，等真有"运维不能改配置"这种压力时再做。

  反对意见：如果老大计划让多租户用户各自配 MCP server（每个用户接自己的 GitHub
  MCP token），(A) 就不够用了，得是 (C) 加 per-user 配置。这是一个产品方向问题。

  老大选哪个？另外明确一下：这次接入的 MCP server 是公开生态的（如 GitHub 
  MCP）、内部业务的、还是先留个空配置只做框架？

  问题 8 / Progressive disclosure 的 Java 落地方式（Skill 设计的核心）

  这一题决定一切——它直接决定 Skill 在 ChatClient 调用链里的角色、是否需要改
  AgentOrchestrator、模型 prompt 长什么样。

  三种候选：

  (b1) 一个元工具 load_skill(name) + system prompt 列举 skill 清单
  - 启动扫描 → SkillRegistry
  - system prompt 追加：「可用 skills（按需调用 load_skill 加载完整内容）：- 
  pdf-analysis: 解析 PDF...; - sql-style: SQL 风格指南...」
  - 注册一个元工具 load_skill(name) 到 ToolRegistry
  - 模型决定需要时 → toolcall load_skill("pdf-analysis") → 返回 SKILL.md 全文 →
  Spring AI 自动把全文作为 tool result 回灌到下一轮 → 模型在新上下文里使用
  - 这正是 Anthropic 原版语义的字面翻译

  (b2) 每个 skill 注册为独立虚拟工具
  - 每个 skill = 一个 ToolDescriptor，name = skill 名，description = frontmatter
   的 description
  - 模型直接 toolcall 该 skill，返回 SKILL.md 全文
  - 工程上最自然（完全复用 Spring AI tool calling），Pattern A 落地最干净
  - 但语义降维——把 skill 等同于 tool，丢失 Anthropic 设计里"skill
  是独立概念，不是 tool"这层抽象

  (b3) Advisor 拦截特殊 token（如 <load-skill>pdf-analysis</load-skill>）
  - 用 Spring AI Advisor 在生成阶段解析模型输出
  - 需要可靠的格式约定、模型遵循度难保证
  - 与原版机制差异最大

  对比表：

  1. 动机决定路径：刚才确认动机是 (iii)「忠于原版」，b1 是 Anthropic 原版的字面
  1:1 翻译——name+description 在 system prompt 列举、模型 explicit
  load、内容作为返回值进上下文。b2 虽然工程上更顺，但抹掉了"skill ≠ tool"这层 
  Anthropic 故意保留的抽象，与 (iii) 的精神矛盾。
  2. 可写文章的价值：(iii) 隐含目标是写笔记进 docs/notes/，b1

  4. 未来可演进：b1 → b2 是单向门可走的（如果将来发现某些 skill

● ---
  问题 10 / Skill 是否支持可执行内容（scripts/ 子目录）

  Anthropic 原版的 Skill bundle 经常带 scripts/ 子目录，里面是 Python/shell
  脚本。Claude Code 这类 agent 读完 SKILL.md 后，会用自己的 Bash tool
  主动执行这些脚本（比如 PDF 解析 skill 里的 parse.py）。

  dawn-ai 落地有三种选择：

  Column 1: 安全风险
  (A) 完全不支持 scripts/: 0
  (B) 允许 scripts/ 存在，仅作"文件清单"暴露给模型，不执行: 0
  (C) 支持沙箱执行: ⚠️ 高（任意代码执行）
  ────────────────────────────────────────
  Column 1: 工程复杂度
  (A) 完全不支持 scripts/: 0
  (B) 允许 scripts/ 存在，仅作"文件清单"暴露给模型，不执行: 低
  (C) 支持沙箱执行: 极高
  ────────────────────────────────────────
  Column 1: 忠于原版
  (A) 完全不支持 scripts/: ❌ 偏离
  (B) 允许 scripts/ 存在，仅作"文件清单"暴露给模型，不执行: ⚠️
    部分（结构在，执行权不在）
  (C) 支持沙箱执行: ✅ 完全
  ────────────────────────────────────────
  Column 1: 用户体验
  (A) 完全不支持 scripts/: 干净
  (B) 允许 scripts/ 存在，仅作"文件清单"暴露给模型，不执行: ⚠️
  困惑：「模型说要跑
    parse.py，但跑不了」
  (C) 支持沙箱执行: 强大
  ────────────────────────────────────────
  Column 1: dawn-ai 现状契合
  (A) 完全不支持 scripts/: ✅ 没有 shell tool，scripts/ 本来也跑不起来
  (B) 允许 scripts/ 存在，仅作"文件清单"暴露给模型，不执行: 同左但暴露困惑
  (C) 支持沙箱执行: 需要先做 shell tool + 沙箱

  我推荐 (A) 完全不支持 scripts/，理由：

  1. dawn-ai 没有 shell/bash tool——scripts/ 子目录就算放着也无能力执行，(B)
  会让模型在 plan 里写出"我要跑 parse.py"然后空转，体验差。

  问题 14 / 最后一组小决策（打包确认）

  (1) 选择性激活
  推荐：全局可见（所有 skill 列入 system prompt，模型自主决策）。理由：(iii)
  忠于原版语义；dawn-ai 没有租户/角色体系，做激活范围过早抽象。

  (2) 内置示例 skill 是什么
  推荐：code-review-zh —— 一个"中文代码 review 风格指南" skill。SKILL.md
  写"如何用中文 review Java 代码、风格、命名、错误处理"；references/checklist.md
   列详细 checklist。理由：① 与项目本身的工程感契合（dawn-ai 是 Java 项目）；②
  演示截图自然（"帮我 review 这段代码"→ 模型 load skill → 按风格给反馈）；③
  中文，符合用户偏好。

  (3) system prompt 里 skill 清单的格式
  推荐：Markdown 列表，例如：
  ## 可用 Skills
  按需调用 `load_skill(name)` 加载完整指令。需要 skill 的内嵌资源时调用
  `read_skill_resource(skill, path)`。

  - **code-review-zh**: 中文代码 review 风格指南，处理"帮我 review
  这段代码"类需求时使用
  - **pdf-analysis**: ...
  理由：人类可读 + LLM 友好，比 JSON 短，比自然语言段落结构化。

  (4) skill 名字符约束
  推荐：kebab-case，正则 ^[a-z][a-z0-9-]{0,63}$。理由：与 Anthropic
  原版一致；URL/路径友好（reload endpoint 可能要带 name）；防各种 escape
  坑。违反规则 → 拒绝注册 + ERROR 日志。

  (5) description 长度上限
  推荐：1024 字符硬上限（超过截断 + WARN 日志）。理由：description 永久驻留
  system prompt，每次 chat 都要付 token；1024 字符（≈ 中文 500 字 / 英文 200
  词）足够写清"何时触发该 skill"，再长就该写进 SKILL.md 正文了。

  (6) 命名空间 / 命名冲突
  确认：不存在冲突。ToolRegistry 里只多 2
  个工具（load_skill、read_skill_resource），与现有
  KnowledgeSearchTool/WeatherTool/CalculatorTool 不重名。skill 名是 load_skill
  的参数，不进工具命名空间。

  (7) 可观测性
  确认：自动复用。load_skill / read_skill_resource 都是 Spring Bean + Function +
   @Description，会被 ToolRegistry 自动发现，被 ToolExecutionAspect 自动拦截 →
  StepCollector 记录 → SSE step 事件推送 → Langfuse span 自动产生。零额外工作。

  (8) 分支命名
  推荐：feat/skill-support。理由：仓库现有约定从 git log 看是 feat/... /
  docs/...（如 feat/langfuse-integration）。
